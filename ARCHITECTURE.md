# Архитектура проекта: BookWave

Базовая (верхнеуровневая) архитектура на основе [BookWave_TZ.md](BookWave_TZ.md).

Фундамент — modular monolith на Django, отдельный Flutter-клиент и отдельная
web SPA администратора, оба через единый REST API. Ниже — компоненты,
модель данных, ключевые сценарии и открытые вопросы, требующие решения до
начала реализации.

## Компоненты системы

```
┌───────────────────────┐     ┌──────────────────────┐
│  Mobile App             │     │  Admin SPA             │
│  (Flutter / Dart)       │     │  (React + TypeScript)  │
│  читатели, iOS/Android  │     │  админы/контент-мен.  │
└───────────┬────────────┘     └───────────┬───────────┘
            │                              │
            │        HTTPS / REST API      │
            └───────────────┬──────────────┘
                             │
                  ┌──────────▼───────────┐
                  │  Backend               │
                  │  Django + DRF           │
                  │  (modular monolith)    │
                  └──────────┬───────────┘
                             │
         ┌───────────────────┼───────────────────┬──────────────┐
         │                   │                   │              │
┌────────▼────────┐  ┌────────▼────────┐  ┌────────▼────────┐  ┌▼──────────┐
│ PostgreSQL         │  │ Файловое         │  │ Email (SMTP)     │  │ Push (лог) │
│ (данные)           │  │ хранилище        │  │ уведомления      │  │ уведомления│
│                    │  │ (локально / S3)  │  │                  │  │            │
└────────────────────┘  └─────────────────┘  └─────────────────┘  └────────────┘
```

Admin-панель зафиксирована как отдельное SPA-приложение (React +
TypeScript, см. «Открытые вопросы» п.2), а не как Django-шаблоны: ТЗ явно требует
"отдельное веб-приложение через тот же REST API", а не серверный рендеринг.

## Backend (Django + DRF)

Domain-oriented apps:

- **users** — регистрация, авторизация (JWT), роли (гость/читатель/админ), сброс пароля, профиль, аватар
- **catalog** — книги, жанры, авторы, поиск/фильтры/сортировка, soft delete
- **files** — загрузка и защищённая выдача обложек и файлов книг (EPUB/PDF/FB2)
- **favorites** — избранное
- **cart** — корзина
- **orders** — заказы, состав заказа, статусы, атомарный checkout
- **promo** — промокоды и их использование
- **library** — библиотека пользователя, прогресс чтения, синхронизация
- **bookmarks** — закладки
- **reviews** — отзывы и рейтинги
- **reports** — статистика продаж, экспорт в xlsx/csv (админ)
- **notifications** — email и push уведомления, пользовательские настройки категорий

Cross-cutting-задачи, не привязанные к одному app:

- permissions (роль на каждом защищённом эндпоинте)
- JWT lifecycle (выдача, revocation)
- серверная валидация входных данных (типы, длины, форматы, диапазоны)
- атомарные транзакции для многошаговых операций (checkout)
- backup БД и файлового хранилища

## База данных — PostgreSQL

Таблицы (snake_case), включая ранее упущенные при первом черновике:

- `users` — учётные данные, роль, тема/язык интерфейса, аватар
- `books` — метаданные, цена, ISBN, `is_active` / `deleted_at` (soft delete)
- `genres`, `authors` — справочники
- `book_authors` — M2M книга↔автор (у книги может быть несколько авторов)
- `book_genres` — M2M книга↔жанр, либо FK на `genres`, если книга — один жанр (решить явно, см. открытые вопросы)
- `favorites` — пользователь↔книга
- `carts`, `cart_items` — корзина и её позиции
- `orders`, `order_items` — заказы и состав заказа
- `promo_codes`, `promo_code_usages` — промокоды и их применения
- `user_library` — пользователь↔книга, прогресс чтения, `progress_updated_at` (для разрешения конфликтов синхронизации)
- `bookmarks` — пользователь↔книга↔позиция в тексте
- `reviews` — пользователь↔книга, текст, оценка
- `notification_preferences` — пользователь↔категория уведомления↔вкл/выкл
- `device_tokens` — пользователь↔push-токен устройства
- `email_confirmation_tokens`, `password_reset_tokens` — служебные, со сроком действия
- `banners` — карусель баннеров новинок/акций на главной (изображение, ссылка на книгу/раздел, период показа)

## Ключевые сценарии (обязательны к соблюдению в реализации)

**Checkout (оформление и оплата заказа)** — одна атомарная транзакция
(`transaction.atomic()`), чтобы система не могла оказаться в промежуточном
состоянии "заказ оплачен, но книга не выдана":

```
validate promo (срок, минимальная сумма, лимит использований)
→ create order (status = "оплачен")
→ create user_library entries для всех книг заказа
→ record promo_code_usage
→ clear cart
→ commit
→ send email с чеком
```

**Чтение / синхронизация прогресса** — конфликт между устройствами
разрешается по времени последнего сохранения:

```
authorize: книга есть в user_library текущего пользователя?
→ отдать файл (см. "Раздача файлов книг")
→ клиентская читалка сохраняет progress + updated_at
→ на сервере: incoming.updated_at > stored.updated_at → обновить
```

**Смена пароля** — после успешной смены все прочие активные сессии
пользователя должны быть завершены. Со stateless JWT это не происходит
автоматически — нужен явный механизм revocation (blacklist уже выданных
токенов либо `user.token_version`, инкрементируемый при смене пароля и
проверяемый при каждой авторизации).

**Блокировка входа после 3 неудачных попыток** — состояние счётчика
попыток недолговечно, хранить его в БД избыточно: использовать Django
cache (при необходимости — Redis), не отдельную таблицу.

**Подтверждение e-mail при регистрации** — ТЗ одновременно требует
автоматический вход сразу после регистрации и письмо с подтверждением
адреса. Принятое правило: аккаунт активен и залогинен сразу,
`email_verified = false` до перехода по ссылке из письма; неподтверждённый
адрес не блокирует использование приложения.

## Раздача файлов книг

Авторизация — всегда на Django (проверка принадлежности книги библиотеке
пользователя), но сами байты (файлы до 100 МБ) не должны идти через
Gunicorn/uWSGI воркер:

- локальное хранилище — `X-Accel-Redirect` во внутреннюю `location` Nginx
- S3-совместимое хранилище — временная подписанная ссылка, выдаваемая
  после проверки прав

Прямых публичных URL на файлы книг нет в обоих случаях.

**Ознакомительный фрагмент (без покупки)** — ТЗ требует, чтобы фрагмент
(первые 10-15% книги) был доступен для чтения даже роли «Гость», то есть
без записи в `user_library`. Это не отдельный предзагруженный файл-превью
(усложнение при загрузке книги на каждый формат) и не смягчение общего
запрета на прямые ссылки — тот же защищённый эндпоинт, что и для полного
файла, но с серверным ограничением объёма отдаваемых данных: если
запрашивающий пользователь (или гость) не владеет книгой, эндпоинт отдаёт
только первые 10-15% (по числу страниц/символов, а не по байтам файла —
чтобы не обрезать файл посреди структуры формата). Реализуется в Phase 6
вместе с остальной раздачей файлов.

## Читалка (Mobile App)

Отдельный, самый нетривиальный модуль клиента, не просто ещё один экран:

```
Reader
 ├─ EPUB renderer (основной, полная функциональность)
 ├─ PDF/FB2 viewer adapters (базовый просмотр через готовые библиотеки)
 ├─ Reader settings (шрифт, тема: светлая/тёмная/сепия)
 ├─ Table of contents
 ├─ Bookmarks
 ├─ Full-text search
 └─ Progress sync (см. сценарий выше)
```

## Mobile App (Flutter) — остальные слои

UI/экраны → state management (Riverpod, см. «Открытые вопросы» п.3) →
сервис работы с REST API → локальный кеш (сессия, тема, язык).

## Admin Web Panel

Отдельное SPA (React + TypeScript + Vite), взаимодействующее с backend только через REST
API — то же API, что использует мобильное приложение.

**Баннеры** — ТЗ не требует отдельного экрана управления баннерами ни в
одном из перечисленных экранов админ-панели, поэтому контентом `banners`
управляют через встроенную Django-админку (`BannerAdmin` уже
зарегистрирован в `apps/banners/admin.py`) — отдельный экран в
admin-panel не нужен. Мобильному приложению нужен только публичный
`GET`-эндпоинт списка активных баннеров (Phase 3). Баннер ведёт либо на
книгу (`link_book`), либо в раздел каталога (`link_url` = `catalog` или
`catalog?genre=<id>`).

## Уведомления

- **Email** — регистрация (подтверждение адреса), сброс пароля, успешная оплата (чек)
- **Push** (заглушка с логированием вместо FCM/APNs, см. «Открытые вопросы» п.9) — по категориям: новинки, статус заказа, ответы на отзывы; управляются пользователем в настройках, статус хранится в `notification_preferences`, токены устройств — в `device_tokens`

## Рекомендации на главной

Без ML: подбор книг по жанрам избранного и уже купленных книг, исключая то,
что уже есть в библиотеке. Реализуется как сервисная функция внутри
`catalog`/`library` (например, `catalog.services.get_recommendations(user)`),
отдельный сервис для этого не нужен.

## Поиск и производительность каталога

PostgreSQL достаточно для объёма курсового проекта, отдельный поисковый
движок не нужен. Обязательные индексы: `books.is_active`, `books.isbn`,
`books.created_at`, `books.price`, FK на `genres`/`authors`; `authors.name`
индексирован через `unique`. Отдельного индекса на `books.title` нет:
поиск идёт по `icontains` (подстрока без учёта регистра), обычный B-tree
индекс его не ускоряет. При росте данных — full-text/trigram индексы
PostgreSQL как опциональная оптимизация.

## Развёртывание (упрощённо)

```
Nginx (reverse proxy + HTTPS, X-Accel-Redirect для файлов книг)
  → Gunicorn/uWSGI → Django/DRF
  → PostgreSQL + файловое хранилище

Backup (регулярно, обязательное требование ТЗ)
  ├── PostgreSQL dump
  └── файловое хранилище (обложки, книги)
        → внешний носитель / облако
```

Реализация: `python manage.py backup` (`apps/common/management/commands/backup.py`)
— создаёт `pg_dump` (custom-формат) БД и `tar.gz` каталога `media/` в
`BACKUP_DIR` (по умолчанию `backend/backups/`, не коммитится). Сама
команда только создаёт архивы за один запуск; регулярность и доставка на
внешний носитель/в облако — системная задача, не код Django:

- прод (Linux): cron-задача (`crontab -e`), например ежедневно в 03:00 —
  `0 3 * * * cd /path/to/backend && venv/bin/python manage.py backup`,
  где `BACKUP_DIR` указывает на примонтированный внешний диск/облачное
  хранилище (rclone mount, S3-совместимый бакет и т.п.);
- восстановление: `pg_restore -d bookwave db_<ts>.dump` и распаковка
  `media_<ts>.tar.gz` в `MEDIA_ROOT`.

Flutter-приложение собирается отдельно и распространяется как APK/IPA (или
через сторы).

Реализация (Phase 11): `backend/Dockerfile` + `backend/entrypoint.sh`
(migrate → collectstatic → gunicorn), `admin-panel/Dockerfile`
(multi-stage: сборка Vite → тот самый Nginx из схемы выше, отдаёт SPA и
проксирует `/api/`, `/admin/`, статику/медиа на backend, с internal-location
под X-Accel-Redirect — конфиг в `admin-panel/nginx.conf`), всё вместе —
`docker-compose.yml` (`docker compose up -d --build`, см. README.md).
Локальный docker-compose — без реального домена/TLS-сертификата, поэтому
`SECURE_SSL_REDIRECT`/`SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE`
переопределены в `False` через `environment:` в docker-compose.yml (в
`config/settings/prod.py` эти флаги читаются из env, по умолчанию `True` —
для реального продакшена за TLS-терминатором ничего менять не нужно).
Живьём проверено: миграции/статика/gunicorn поднимаются, API и
Django-админка (сессионный логин, CSRF) отвечают через прокси по HTTP,
`/media/books/` и `/protected-media/` закрыты снаружи как и задумано.
Уточнения по итогам Phase 12: в Nginx задан `client_max_body_size 310m`
(форма книги шлёт обложку и до трёх файлов по 100 МБ одним запросом), в
образ backend добавлен `postgresql-client` 17, чтобы `manage.py backup`
работал внутри контейнера. `TIME_ZONE` по умолчанию `Europe/Moscow`
(хранение в UTC, границы суток в отчётах — по поясу магазина).

## Открытые вопросы (все закрыты)

1. ~~`book_genres` — M2M или FK (один жанр на книгу)?~~ Решено: **M2M**
   (`Book.genres`, `db_table="book_genres"`) — у книги может быть
   несколько жанров.
2. ~~Конкретный фреймворк Admin SPA (React vs Vue).~~ Решено: **React** — см. [README.md](README.md#структура-проекта).
3. ~~State management для Flutter.~~ Решено: **Riverpod** (`flutter_riverpod`) — зафиксировано в `AGENTS.md`.
4. ~~JWT revocation — blacklist токенов vs `token_version`.~~ Решено:
   **`token_version`** — поле на `User`, инкрементируется при смене/сбросе
   пароля, сверяется в `TokenVersionJWTAuthentication`
   (`apps/users/authentication.py`) с одноимённым claim в токене.
   Уточнение (Phase 9): т.к. `token_version` глобальный, инкремент при
   смене пароля инвалидирует и токены устройства, с которого её выполнили
   — а ТЗ требует завершать только "прочие" сессии. Поэтому
   `ChangePasswordView` выдаёт свежую пару access/refresh в ответе (как
   `LoginView`) — вызывающая сторона обязана её сохранить. Сброс пароля по
   e-mail (`PasswordResetConfirmView`) новых токенов не выдаёт намеренно —
   там нет "текущего устройства", пользователь и так не аутентифицирован.
5. ~~Локальное хранилище vs S3 для файлов книг на первом этапе.~~ Решено для Phase 1: **локальное** (Django `FileSystemStorage`, `backend/media/`). S3 остаётся возможной миграцией перед продакшеном, но не блокирует текущую разработку.
6. ~~Как отдавать ознакомительный фрагмент без записи в библиотеке, не
   нарушая запрет на прямые ссылки?~~ Решено: тот же защищённый эндпоинт,
   что и для полного файла, с серверным ограничением объёма для
   невладельцев — см. «Раздача файлов книг».
7. ~~Нужен ли отдельный экран управления баннерами в admin-panel?~~
   Решено: нет, ТЗ его не требует — Django-админка (`BannerAdmin`)
   достаточна, см. «Admin Web Panel».
8. ~~Конкретные границы длины текста отзыва?~~ ТЗ (п. 4.5.4) требует
   серверную валидацию длин/диапазонов входных данных, но не называет
   число для текста отзыва. Решено: 10–2000 символов при непустом тексте
   (`Review.text`, `apps/reviews/validators.py`); текст остаётся
   необязательным — можно оставить только оценку.
9. ~~Реальный Firebase/FCM для push или заглушка?~~ Решено окончательно
   (не временное решение до продакшена): push-уведомления реализованы как
   заглушка — локальный псевдо-токен на клиенте + логирование на бэкенде —
   на постоянной основе; переход на реальный Firebase/FCM не планируется.
   ТЗ не требует конкретной технологии доставки push, только наличие
   управляемых пользователем категорий уведомлений — это требование уже
   выполнено независимо от способа доставки.
10. ~~Отмена заказа пользователем (ТЗ упоминает её только как пример
    необратимого действия, требующего диалога подтверждения, — п.
    «Отказы из-за некорректных действий пользователя»; отдельного
    пользовательского сценария/экрана отмены заказа ТЗ нигде не
    описывает).~~ Решено (Phase 11): пользовательская отмена оплаченного
    заказа **не реализуется** — не требуется явно ни в одном другом
    пункте ТЗ. Статус `Order.Status.CANCELLED` уже существует в модели
    как значение, которое администратор может проставить вручную через
    admin-панель (Phase 10, модерация заказов) — этого достаточно, чтобы
    статус «Отменён» имел смысл в истории заказов пользователя. Диалог
    подтверждения для этого действия закрывается автоматически: раз
    действия нет на клиенте, подтверждать нечего.
11. ~~Локализация интерфейса (RU/EN) — не реализована (числилась в
    «Известных ограничениях» с Phase 9).~~ Решено: полная локализация
    экранов через `flutter_localizations`/`intl` — ARB-источники
    `mobile/lib/l10n/app_ru.arb` и `app_en.arb`, сгенерированный
    `AppLocalizations` (пересобирается автоматически, `generate: true`
    в `pubspec.yaml`, не коммитится), `MaterialApp.locale` привязан к
    `User.language` (`app.dart`, `_localeFor`). Переведены все строки
    presentation-слоя (экраны/виджеты) и дефолтные сообщения об ошибках
    в `*_exception.dart` — для последних, т.к. это фабричные конструкторы
    без `BuildContext`, добавлен `core/current_locale.dart`
    (модульная переменная текущей локали, обновляется из `app.dart`
    вместе с `MaterialApp.locale`) и используется через
    `lookupAppLocalizations(currentAppLocale)`. Не переводятся:
    контентные данные с бэкенда (названия книг/жанров/авторов,
    описания, тексты отзывов — это данные, а не UI) и сообщения об
    ошибках, приходящие от сервера как есть (`{"detail": "..."}` в
    ответе DRF) — их локализация потребовала бы i18n на бэкенде,
    отдельная, не запрошенная задача. Форматирование дат заказов
    (`order_date_format.dart`) переведено на `intl`-`DateFormat` с
    учётом локали вместо захардкоженных русских названий месяцев.
