я# Инструкции для агента — проект BookWave

Эти правила действуют для **всех** сессий и всех частей проекта (backend,
mobile, admin-panel). Перед началом работы прочитай `BookWave_TZ.md`
(техническое задание) и `ARCHITECTURE.md` (архитектурные решения) — это
источники истины. Если текущая задача им противоречит — сообщи об этом,
не решай молча в обход документов.

## 1. Git — без самодеятельности

- **Никогда** не выполняй `git commit` и `git push` без явного запроса
  пользователя в текущем сообщении. Подготовил изменения — остановись и
  скажи, что готово, дальше решает пользователь.
- Не создавай и не переключай ветки самостоятельно, если не попросили.
- Не трогай `.git`, `.gitignore`, CI-конфиги без явного запроса.

## 2. Когда спрашивать, а когда действовать

Спрашивай, прежде чем действовать, если:
- решение необратимо или дорого отменить (миграция БД, удаление данных,
  смена ключевого фреймворка/библиотеки);
- вопрос уже зафиксирован в ARCHITECTURE.md как "открытый" и всё ещё не
  закрыт — не выбирай сам, спроси;
- задача требует нового стороннего пакета/зависимости, которой ещё нет в
  проекте — сначала спроси, какую именно ставить и зачем;
- требование в ТЗ неоднозначно или противоречит уже написанному коду.

Не спрашивай и просто делай, если:
- решение уже зафиксировано в ARCHITECTURE.md или в этом файле;
- это рутинная реализация внутри уже согласованной структуры (новый метод
  в существующем сервисе, новый экран внутри уже созданной фичи).

## 3. Структура папок — соблюдать строго

- Backend: domain-oriented Django apps, как перечислено в
  ARCHITECTURE.md (`users`, `catalog`, `files`, `orders` и т.д.). Новый
  функционал кладётся в существующий app по смыслу; новый app создаётся
  только если функциональность действительно не относится ни к одному из
  существующих — и это тот случай, когда нужно спросить, а не решать самому.
- Flutter: **feature-first**, слои (`data/domain/presentation`) — внутри
  каждой фичи в `lib/features/<feature>/`. Общий код — только в `core/`
  (сквозная инфраструктура: сеть, кеш, ошибки) и `shared/` (модели,
  утилиты, используемые в 2+ фичах). Не создавай общую свалку `screens/`,
  `models/`, `services/` на весь проект.
- Admin SPA: React + TypeScript + Vite, структура зеркалит backend apps
  (по фичам, не по типу файла).
- Не переименовывай и не перемещай существующие файлы/папки без явного
  запроса — рефакторинг структуры делается отдельной обсуждённой задачей.

## 4. ООП — строго и осознанно

- Явное разделение ответственности: модели/сущности отдельно от бизнес-
  логики, бизнес-логика отдельно от I/O (HTTP, БД, файлы).
- Инкапсуляция: не тянуть внутренние детали одного слоя в другой
  (например, ORM-модель Django не должна "протекать" напрямую в
  presentation-слой Flutter — только через DTO/сериализатор).
- Предпочитай композицию наследованию, если нет явной иерархии "is-a".
- Интерфейсы/абстракции — только там, где реально больше одной реализации
  или это явно потребуется по ТЗ (например, адаптеры PDF/FB2 в читалке).
  Не создавай абстракцию "на будущее" без текущей необходимости — см. п.6.
- Единая ответственность класса/сервиса: если класс делает больше одной
  вещи — раздели.

## 5. Тесты — только по существу

- Не пиши тесты, если явно не попросили либо если это не критичная логика
  (см. список ниже). Задача — рабочий код курсового проекта, а не 100%
  покрытие.
- Тесты обязательны без дополнительного напоминания только для:
  - расчётов и валидации промокодов;
  - checkout-транзакции (атомарность, откат при ошибке);
  - логики разрешения конфликта синхронизации прогресса чтения;
  - контроля доступа к файлам книг (проверка принадлежности библиотеке).
- Не генерируй тесты-заглушки "для галочки" (пустые/тривиальные assert
  True). Если тест ничего не проверяет — не создавай его.

## 6. Не плодить лишние сущности

- Не создавай классы, DTO, интерфейсы, таблицы БД или файлы "на будущее",
  если под них нет текущей задачи в ТЗ или в этой сессии.
- Не дроби функциональность на избыточное количество мелких файлов/модулей,
  если это не улучшает читаемость (см. правило "одна ответственность" —
  но не доводи его до абсурда).
- Новая таблица в БД — только если её нет в списке ARCHITECTURE.md и она
  реально нужна; если нужна, но списка нет — спроси, прежде чем создавать.

## 7. Перед новым кодом — проверь, нет ли уже такого

- Перед созданием функции/класса/эндпоинта — поищи по проекту, нет ли уже
  аналогичной или похожей реализации, которую можно переиспользовать или
  расширить.
- Если находишь дублирующуюся логику в разных местах при работе над
  задачей — сообщи и предложи объединить (но не объединяй сам без
  подтверждения, если это большой рефакторинг).

## 8. Чистка неиспользуемого кода

- Если по ходу задачи видишь мёртвый код (неиспользуемые импорты, функции,
  переменные, файлы, закомментированные блоки), который явно относится к
  зоне твоих изменений — удаляй.
- Не устраивай отдельную ревизию всего проекта на мёртвый код без запроса —
  чисти только то, что встретил по пути.

## 9. Общий стиль работы

- Один логический кусок работы — за раз. Не смешивай в одном заходе
  реализацию функционала и попутный рефакторинг несвязанных частей.
- Секреты, ключи, токены, пароли — никогда не хардкодить в код и не
  коммитить в репозиторий; только через переменные окружения / `.env`
  (сам `.env` — в `.gitignore`, не создавай его с реальными значениями).
- Именование: backend — `snake_case` (Python, БД, поля API), клиентский
  Dart-код — `lowerCamelCase`, как зафиксировано в ТЗ.
- Не меняй уже принятые архитектурные решения (React, Riverpod для
  Flutter, feature-first структура, JWT-аутентификация и т.д.) без
  явного запроса — считай их закрытыми вопросами, а не предложениями к
  обсуждению.
- Если задача из чата противоречит ТЗ или ARCHITECTURE.md — не следуй ей
  молча и не игноряй её молча. Скажи об этом прямо и уточни, как поступить.

## 10. Коммуникация

- Всегда отвечай на русском языке, независимо от языка запроса.
- Кратко резюмируй, что сделано и что осталось, в конце каждой задачи.
- Если задача оказалась крупнее, чем ожидалось (требует много файлов/
  решений) — предложи разбить на этапы, а не делать всё одним большим
  заходом.

## 11. Пруфы перед сдачей фазы — особенно в автоматическом режиме

- Перед тем как объявить фазу (или крупный кусок задачи) готовой, покажи
  фактическое подтверждение, а не пересказ того, что должно работать:
  реальный вывод команды (`manage.py check`, `makemigrations --check`,
  тесты, smoke-запрос через реальный view/`force_authenticate`,
  запущенное приложение и т.п.). Особенно строго — если работа делалась
  в автоматическом режиме без промежуточных подтверждений пользователя:
  там некому было заметить самодеятельность или халтуру по ходу дела,
  значит подтверждение нужно предъявить постфактум.
- Явно перечисли, чего НЕ добавлено сверх ТЗ/PLAN.md/ARCHITECTURE.md
  (лишние таблицы, зависимости, эндпоинты, экраны, тесты-заглушки) —
  отсутствие лишнего показывается, а не декларируется.
- Если по ходу нашёл несоответствие ТЗ/архитектуре — исправь и покажи
  до/после тем же способом (прогнать проверку заново), не полагайся на
  память о том, что "теперь должно работать".

## 12. Использование плагинов/скиллов

- `humanizer`, `caveman` и `ru text` — включены **по умолчанию** во всех
  сессиях: `caveman` держит ответы и код-ревью сжатыми, `humanizer` —
  правит текст, который выглядит "сгенерированным" (когда пишешь prose
  для пользователя или документацию), чтобы не звучало как типичный
  ИИ-текст, `ru text` — обеспечивает грамотный русский текст в ответах и
  комментариях. Применяй их без напоминаний, там где они уместны по
  своему назначению.
- `superpowers` — **только по явному запросу** пользователя в текущем
  сообщении. Никогда не вызывай и не используй его самостоятельно, даже
  если задача выглядит подходящей — это правило без исключений, аналогично
  git commit/push из п.1.
- Остальные установленные скиллы (code-review, simplify, safe-refactor,
  surgical-patch, migration, investigate-first, verify-and-stop,
  lean-build, planning-with-files, cavecrew, dataviz, artifact-* и т.д.) —
  выбирай сам, по смыслу задачи, без необходимости спрашивать разрешения:
  - код-ревью/поиск багов → `code-review`; чистка без поиска багов →
    `simplify`.
  - точечный багфикс без побочных изменений → `surgical-patch`.
  - структурный рефакторинг с сохранением поведения → `safe-refactor`.
  - схема БД/API/протокол/зависимости с откатом → `migration`.
  - непонятная/нестабильная ошибка перед правкой → `investigate-first`.
  - только проверка, что готовое решение соответствует условиям, без
    расширения объёма → `verify-and-stop`.
  - новая функциональность с риском переусложнения → `lean-build`.
  - крупная многошаговая задача, которую полезно вести файлами
    (task_plan.md и т.д.) → `planning-with-files`.
  - делегирование поиска кода/точечных правок/ревью диффа в подагентов
    для экономии контекста → `cavecrew`.
- Если задача пограничная, но по описанию скилла понятно, какой ближе —
  решай сам, спрашивать не нужно. А если вообще непонятно, какой скилл
  уместен (ни один явно не подходит по описанию, или задача не похожа ни
  на один сценарий) — на всякий случай уточни у пользователя, а не
  выбирай наугад.
