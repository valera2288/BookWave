# План внедрения — BookWave

Порядок фаз соответствует зависимостям между модулями (сначала фундамент,
затем то, что от него зависит), а не разделам ТЗ построчно. Структура
проекта — в [README.md](README.md), архитектурные решения — в
[ARCHITECTURE.md](ARCHITECTURE.md).

1. **Скаффолдинг** — инициализация `backend/` (Django-проект, apps-каркас),
   `admin-panel/` (Vite+React), `mobile/` (Flutter, feature-first). Базовые
   настройки (`.env`, CORS, HTTPS в проде).
2. **Данные и auth** — модели users/catalog/cart/favorites/library/
   bookmarks/reviews/promo/orders/notifications/banners, миграции; JWT
   auth, регистрация, вход, сброс пароля, login lockout (Django cache),
   revocation при смене пароля (`token_version`).
3. **Каталог** — books/genres/authors CRUD (admin API), публичный листинг,
   поиск/фильтры/сортировка, soft delete, рекомендации без ML
   (`catalog.services.get_recommendations`). Сюда же — главная страница
   мобильного приложения: карусель баннеров (публичный `GET` для уже
   заведённого `banners` app — модель и Django-админка есть, API нет),
   блок «Новинки» (сортировка `newest`), блок «Рекомендуем», блок
   «Жанры»-плитки. Блок «Топ продаж» на главной подключается после
   Phase 5 (нужны данные заказов).
4. **Favorites & Cart** — API + экраны Flutter.
5. **Checkout & Orders** — промокоды, атомарный checkout
   (`transaction.atomic`: заказ → library → promo usage → очистка корзины),
   имитация оплаты (успех/неуспех, без реальных платёжных данных), экран
   «Успешный заказ», история заказов, письмо с чеком сразу после оплаты.
6. **Файлы и читалка** — защищённая выдача файлов (X-Accel-Redirect/
   подписанные URL), «Моя библиотека», reader (EPUB полностью, PDF/FB2
   базово), progress sync (last-write-wins). Сюда же — раздача урезанного
   ознакомительного фрагмента (10-15%) без записи в библиотеке (см.
   ARCHITECTURE.md, «Раздача файлов книг»); карточка книги на Phase 3
   получает кнопку «Читать фрагмент» уже с расчётом на этот эндпоинт.
7. **Reviews** — отзывы/оценки, пересчёт среднего рейтинга.
8. **Notifications** — push (FCM) + пользовательские предпочтения по
   категориям (письма о регистрации/сбросе пароля уже отправляются с
   Phase 2, чек — с Phase 5; здесь остаётся только push).
9. **Онбординг, профиль и настройки** — экран загрузки (лого поверх уже
   готового session-restore-гейта в mobile), экран приветствия (3-4
   слайда, «Далее»/«Пропустить»/«Начать», флаг «уже показывали» в
   локальном хранилище), экран «Профиль» (меню: заказы/избранное/
   настройки/выйти), экран «Настройки» (тема/язык/push-категории), UI
   редактирования профиля (имя, аватар, переподтверждение e-mail при
   смене), UI смены пароля (бэкенд — `ChangePasswordView` — уже есть).
10. **Admin-панель** — авторизация администратора (недоступна роли
    «Читатель», аккаунты создаются вручную на сервере, не через публичную
    регистрацию), заказы, модерация отзывов, промокоды, отчёты и экспорт
    xlsx/csv (часть каталога уже покрыта фазой 3; баннеры — через
    Django-админку, отдельный экран не нужен, ТЗ не требует).
11. **Нефункциональные требования** — индексы БД, backup (БД + файлы),
    финальная сверка с чек-листом безопасности из ТЗ (роли на каждом
    эндпоинте, серверная валидация) и с чек-листом подтверждающих
    диалогов перед необратимыми действиями (удаление книги из библиотеки,
    отмена заказа, выход из аккаунта).
12. **Финальная приёмка проекта** — после того как фазы 1-11 сделаны и
    точечные проверки по каждой из них пройдены, отдельный сквозной проход
    по всему проекту целиком (не по одной фазе): построчная сверка
    [BookWave_TZ.md](BookWave_TZ.md) — каждое требование ТЗ действительно
    реализовано и работает так, как описано (не «примерно похоже»), —
    и [ARCHITECTURE.md](ARCHITECTURE.md) — фактическая реализация
    соответствует документированным таблицам БД, ключевым сценариям и
    закрытым «Открытым вопросам»; отдельно — соответствие самому этому
    плану (ничего не забыто, ничего не осталось недоделанным между фазами
    из-за того, что фазы пересекают backend/mobile/admin-panel по-разному,
    см. AGENTS.md о разборе журнала «фаза X сделана» перед стартом). Здесь
    же — сквозной прогон критических пользовательских сценариев вживую
    (регистрация → покупка → чтение → отзыв; администратор → заказ →
    экспорт отчёта), а не по частям, как в фазовых проверках.

    Формат результата — обязателен, устный вердикт «всё соответствует»
    не принимается:
    - Итог аудита — письменная таблица/чеклист вида
      «пункт ТЗ → где реализовано (файл/модуль) → статус», а не общая
      оценка. Только так результат можно проверить, а не принять на слово.
      «Статус» — не бинарный («да/нет»): реализовано / реализовано
      частично / не реализовано; при частичной реализации — явно, чего
      именно не хватает.
    - Аудит **не чинит найденное по ходу**. Сначала — только список
      расхождений (что нашли, где, насколько серьёзно), без правок кода.
      Дальше пользователь решает приоритет и что именно чинить — правки
      идут отдельными задачами после этого решения. Это прямое применение
      AGENTS.md п.2 (спрашивать по важным/необратимым решениям, не решать
      молча за пользователя) — иначе на выходе один неконтролируемый diff
      по всему проекту вместо согласованных правок.
